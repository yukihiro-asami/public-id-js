# 整数キーから生成する決定的な公開ID

仕様 v1 — 2026-10-30承認。和英の提案とNode.js参照実装。

[English](README.md)

## 目的

PostgreSQLで採番した整数を内部キーとして使い、外部にはAESで変換した32桁の16進文字列を出す。同じ用途では異なる整数から同じ公開IDが生じない。行ごとの乱数生成や対応表を必要とせず、内部の主キー・外部キー・JOINには整数を使い続ける。

これは連番をそのまま見せないための難読化である。方式・公開定数・用途を知る人は逆変換できる。秘密の保持やアクセス権限の判定は担わない。

## なぜUUIDではなく、この方式なのか

本案の出発点は、PostgreSQLがすでに一意に管理している整数キーである。求めているのは、その一意性を保ったまま、外部では連番を直接表示しないことである。独立した場所で新しい識別子を生成する必要はないため、既存の整数を決定的に変換する構成を選ぶ。

第一の理由は、一意性の根拠を明快にできることである。ランダムUUID v4では、生成値が重ならないという見込みは乱数生成と確率に基づく。DBの一意制約で重複を拒否することはできるが、生成方法そのものが無衝突になるわけではない。本案は、DBが確保した一意性を、同じ用途内で衝突しない変換によってそのまま外部表現へ引き継ぐ。一意性を新たな確率的前提へ委ねず、採番と変換の性質から説明できる。

第二の理由は、ID生成に必要な実行環境への依存を減らせることである。乱数を利用する方式では、乱数源だけでなく生成器の状態管理も正しさの前提になる。RFC 9562もプロセスのforkなどの状態変化に伴う再シードに注意を求めている。本案では、各IDの生成に乱数を使わず、採番済みの整数・公開定数・用途だけで同じ結果を再現する。仮想環境でUUIDが必ず衝突しやすいと主張するのではなく、この方式では乱数の品質や状態を一意性の根拠に含めずに済むことを選択理由とする。[RFC 9562 §6.9](sources/rfc9562.txt)

第三の理由は、内部と外部のために二つの識別子を保存・管理せずに済むことである。UUIDを内部キーにすると、そのキーは16バイトになる。整数を内部キーに残して外部用UUIDを別に割り当てるなら、通常は追加カラムとその一意索引などで対応を保持する。本案では内部キーを8バイトの整数のまま維持し、外部IDは必要なときに生成する。受け取った外部IDも整数へ戻せるため、対応表の検索を挟まずに内部キーを使える。

この選択は、DBで採番できる構成に適している。DBへ接続する前や、相互に調整できない複数の場所で識別子を生成したい場合には、UUIDの分散生成が利点になる。本案ではその能力よりも、**一意性の根拠をDBに集約し、外部表現だけを変換する単純さ**を優先する。外部IDがUUIDより小さい、あるいはAESを使うから生成が必ず速いという主張はしない。計算コストは後述の測定で示す。

## 仕様

### 整数と公開ID

| 項目 | 定義 |
|---|---|
| 入力整数 | JavaScriptの`bigint`。`0n`以上`9223372036854775807n`以下 |
| AESへの入力 | 16バイト。先頭8バイトをゼロ、末尾8バイトを整数の符号なしビッグエンディアン表現とする |
| 変換 | AES-128で単一ブロックを変換する。パディングなし |
| 出力 | 16バイトを先頭から順に、小文字の16進数32桁で表す。先頭のゼロも保持する |
| 逆変換 | 16進数を16バイトに戻し、同じ鍵でAESを逆変換する。先頭8バイトがゼロで、末尾8バイトが入力範囲内なら`bigint`を返す |

PostgreSQLの`bigint`は8バイトの符号付き整数である。その非負部分を対象とする。通常の採番は1から始めても、変換器自体は0を扱える定義にする。[PostgreSQL 16 数値型](https://www.postgresql.org/docs/16/datatype-numeric.html)

符号化の例は次のとおり。これはAES変換前の値であり、公開IDのテストベクトルではない。

| 整数 | 16バイトの入力を16進数で表したもの |
|---|---|
| `0n` | `00000000000000000000000000000000` |
| `1n` | `00000000000000000000000000000001` |
| `9223372036854775807n` | `00000000000000007fffffffffffffff` |

### 公開定数と用途別の鍵導出

呼び出し側が指定する設定は`info`一つだけとする。

| 項目 | 定義 |
|---|---|
| 鍵導出 | RFC 5869のHKDF（ExtractとExpandの両方）、SHA-256 |
| 入力素材（IKM） | `rainfrog-public-id-v1`のUTF-8バイト列。改行・終端NULを含めない |
| salt | ゼロの32バイト。仕様内の固定値であり、呼び出し側の設定にはしない |
| info | 用途を区別する非空文字列のUTF-8バイト列。上限1024バイト |
| 出力鍵 | 16バイト。AES-128の鍵として使う |
| 導出する時点 | 変換器の初期化時に一度。各IDの変換・逆変換では同じ鍵を使う |

RFC 5869では、salt省略時の値はハッシュ出力長のゼロ列であり、`info`は用途や文脈を鍵導出に結び付ける入力である。本案ではこの役割を使い、公開情報から用途別の変換を再現する。[RFC 5869 §2.2・§3.2](https://www.rfc-editor.org/rfc/rfc5869.html)／[保存した原文](sources/rfc5869.txt)

`info`は、例えば`creator-1/roster/customer`のような安定した用途識別子とする。大文字・小文字の変換、前後の空白除去、Unicode正規化は行わない。UTF-8への変換時に別の文字へ置換されることを避けるため、対応する相手のないサロゲートを含む文字列は拒否する。

物理的なテーブル名から実行時に自動生成するのではなく、用途名として固定する。テーブルを改名しただけでは`info`を変更しない。別のDBやテーブルで整数を独立して採番する場合は、用途の区別もその範囲に合わせる。

### APIと入力検査

APIは次の形とする。

```js
import { createPublicIdCodec } from './reference/public-id.js';

const codec = createPublicIdCodec('creator-1/roster/customer');
const publicId = codec.encode(123n);
const id = codec.decode(publicId); // 123n
```

初期化した変換器が導出済みの鍵を保持する。追加のsalt・秘密鍵・暗号方式の選択引数は設けない。

- `encode`は`bigint`だけを受け付ける。`Number`や数値文字列は暗黙に変換しない。
- `decode`は小文字の16進文字列32桁だけを受け付ける。大文字、`0x`、ハイフン、空白は受け付けない。
- 引数の型が違う場合は`TypeError`、長さ・範囲・形式が違う場合は`RangeError`とする。復号後の形式不一致も`RangeError`とする。
- 逆変換できることと、該当レコードが存在することは別である。存在確認とアクセス権限の確認は利用側で行う。

Node.jsでは`node:crypto`の`hkdfSync`と`createCipheriv`／`createDecipheriv`を使用する。AESの呼び出しは`aes-128-ecb`、IVは`null`、`setAutoPadding(false)`とし、必ず1ブロックだけ処理する。複数ブロックの業務データを暗号化する用途へは拡張しない。[Node.js Crypto API](https://nodejs.org/docs/latest-v24.x/api/crypto.html)

AES-128とSHA-256に固定し、選択肢を増やさない。公開された鍵素材から得る難読化用の変換であるため、鍵長を増やすことによる秘匿性を採用理由にはしない。実際の処理時間は後述する。

## 一意性が成り立つ理由

用途を固定したときの変換を次のように表す。

```text
K = HKDF-SHA-256(公開定数, 固定salt, UTF-8(info), 16バイト)
E(n) = ゼロ8バイト || 整数nのビッグエンディアン8バイト
publicId(n) = hex(AES-K(E(n)))
```

異なる整数の符号化`E(n)`は必ず異なる。固定鍵のAESには逆変換があり、異なる入力ブロックが同じ出力になることはない。16進表現もバイト列を一意に表す。この三つの合成により、同じ用途の異なる整数は異なる公開IDになる。ここは乱数衝突の確率に依存しない。[FIPS 197 §5.1・§5.3](https://doi.org/10.6028/NIST.FIPS.197-upd1)／[保存した原文](sources/nist-fips197-upd1.pdf)

採番済みの整数が一意であることはDB側で確保する。同じ整数を再利用すれば同じ公開IDになる。異なる`info`で得た公開ID同士の無衝突は保証しない。用途をまたいで扱う場合は、URLの経路などが示す用途と公開IDの組で識別する。

## 既存方式との違い

| 観点 | 整数を直接公開 | ランダムUUID v4 | 本案 |
|---|---|---|---|
| 一意性の根拠 | DBでの一意な採番 | 乱数の品質と十分な空間。厳密な重複排除には別途検査 | DBでの一意な採番と単射な変換 |
| 中央での採番 | 必要 | 分散した生成が可能 | 必要 |
| 内部キーの保持サイズ | `bigint`なら8バイト | UUIDを内部キーにすれば16バイト | 内部キーは8バイト |
| 外部の文字列表現 | 十進数なら最大19桁 | 標準のハイフン付き表現は36文字 | 小文字16進数32桁 |
| 元の整数との対応表 | 不要 | 整数と別にUUIDを割り当てる場合は対応を保持 | 不要。逆変換可能 |
| 外部ID生成 | 十進表記への変換 | 乱数生成と形式設定 | 初期化時のHKDFと、各IDでAESを1回 |
| 連番の見え方 | そのまま見える | 連番にならない | 表示は連番にならないが、方式を知れば復元・列挙可能 |

本案のAES出力は16バイトであり、UUIDよりバイナリが小さいわけではない。内部整数を維持する利点と外部表現の長さを分けて評価する。UUIDには複数の方式があり、この比較はランダムUUID v4を対象とする。[RFC 9562 §4・§5.4](https://www.rfc-editor.org/rfc/rfc9562.html)／[保存した原文](sources/rfc9562.txt)

## 設計上の選択と先行議論

**なぜAESを使うのか。** 有限の入力を重複なく並べ替え、逆変換できる性質を利用する。新しい暗号アルゴリズムの提案ではない。公開定数なので、暗号としての秘密鍵管理は発生しない。

**なぜ元の整数と同じ長さにしないのか。** 本案は128ビットの出力をそのまま受け入れる。任意の有限領域を扱う先行研究では、出力を元の領域に収めるために繰り返し変換する方法などがある。本案にはその条件がないので、AESを1回適用する構成に留める。これは先行手法との関係の整理であり、本案そのものの新規性を主張するものではない。[Black・Rogaway, Ciphers with Arbitrary Finite Domains, §4, 2002](https://web.cs.ucdavis.edu/~rogaway/papers/subset.pdf)

**なぜHKDFを使うのか。** 用途名を共通の手順で固定長のAES鍵に変換し、同じ用途から同じ変換を再現するためである。公開情報に秘密性を加えるためではない。

**公開後もIDを保つには。** 公開定数、符号化、アルゴリズム、`info`を一組の仕様として固定する。公開ID自体に版番号は埋め込まない。本案を採用した用途では、ライブラリを更新してもこの対応を変えない。将来別方式を作る場合は、既存IDを読む手順を維持する。

## 参照実装の実行

Node.js 24以降を使う。外部パッケージやインストール作業は不要。本提案のディレクトリで次を実行する。

```sh
cd reference
npm test
npm run benchmark
```

DBドライバーから整数を文字列で受け取る場合は、`BigInt(value)`で明示的に変換し、`Number`を経由させない。変換器自体はDBへ接続しない。

## 検証結果

Nodeのテスト8件がすべて成功した。

- AES-128の既知ベクトルと逆変換、RFC 5869のSHA-256ベクトルA.1・A.3。
- 日本語・空白を含む4用途、36件の固定ベクトルの両方向照合。期待値はPython標準のHMACとOpenSSL 3.6.3のCLIで別途生成した。テストではHKDFを明示的に組み立て、ゼロIVのWebCrypto AES-CBCの先頭ブロックでもAESの結果を照合した。内部の暗号ライブラリは共有され得るため、完全に独立したAES実装同士の検証とは主張しない。
- 整数の上下限、ビット・バイト境界、`2^53`を超える整数の精度、出力の先頭ゼロの保持。
- 1万件の連続整数について往復、再現性、出力の重複がないこと。
- 型違い、範囲外の整数、非正規な16進表現、不正な復号形式、不正なUnicode、UTF-8バイト数の上限。

[固定ベクトル](reference/vectors.json)には公開の導出鍵・入力ブロック・出力を収録し、[テスト](reference/public-id.test.js)で再確認できる。有限のスイープ試験は実装の確認であり、一意性の根拠は前述の単射性の説明に置く。誤った用途での復号拒否を認証保証として扱わない。
